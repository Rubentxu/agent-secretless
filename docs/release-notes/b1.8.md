# B1.8 — audit gaps become visible

B1.8 closes audit finding H-02: a failed durable audit write used to be
discarded by the dispatcher, so an operation could succeed while its audit
record never landed and nothing anywhere said so. `append()`'s `Result`
return (v0.39.0) existed precisely so call sites could surface the gap;
the main call site was the one that did not.

## What B1.8 ships

- A sticky `audit_write_failures` counter on the broker, set at the
  dispatcher and logged with `tracing::error` when a handled request's
  audit record fails its durable write.
- The count rides `Response::Pong` with `#[serde(default)]`, so `asv
  status --json` reports it and the human output names the gap in
  operator language, only when it is non-zero. Old brokers read as 0;
  old CLIs ignore the field — both directions pinned by wire tests.
- The count is never reset: the operator who saw the gap keeps being
  able to trust the report after it heals.

## Falsification

The dispatcher test observed RED before the fix (counter stayed 0 while
the durable write failed) and GREEN after. The ephemeral real-process
check drove a real `asv-brokerd` whose audit file was made to fail
(RLIMIT_FSIZE, SIGXFSZ ignored) and asserted the full observable chain
through the product surface: `status --json` 0 then 1, the human
warning, a live broker, an unchanged durable file, and the error line
on the broker's own stdout. That check retires with the block; the
dispatcher test and the wire tests are the permanent half.
